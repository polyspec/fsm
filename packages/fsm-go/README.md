# github.com/polyspec/fsm-go

[한국어](README.ko.md)

The go consumer of fsm (`docs/plans/fsm-v1.md`, C-2). The module is private and is a test bed: it is not published. It shows
how the generated go code of a fsm definition is used, and it checks that code against the conformance vectors. The generated
code of `src/` imports only the standard library; the orm packages are needed by the persistence example alone.

## Generate into your project

Run the generator in the module of your project, which has a `go.mod` such as `module example.com/app`. `--out` is the `src`
directory of that module, because each machine imports `<module>/src/fsm` for the shared `Error` type:

```sh
cd /path/to/app
fsm-gen gen --project /path/to/order-machines --kind go --go-module example.com/app --out ./src
```

```text
[fsm-gen] gen: ok
```

The generated files are not edited by hand. Run the command again after every change of the definition. The vectors are
written by `fsm-gen vectors --kind go` into a test file of your own; the test bed writes them to `tests/vectors_test.go`.

## Generated files

| File | Content |
|---|---|
| `src/fsm/fsm.go` | the package `fsm`: the `Error` type, and the error codes `CodeConflict`, `CodeInvalidTransition`, `CodeUnknownCode` and `CodeReservedCode` (the values `E_CONFLICT` and so on) |
| `src/order/order.go` | the package `order`, one per machine: the types `State` (`int32`, the code), `Event` (`int32`, the position from 1) and `Step`, the constants `StateDraft`… and `EventNext`…, and the functions of the machine |

Each file starts with `// Code generated by fsm-gen from <machine>; DO NOT EDIT.`, so `fsm-gen gen` can tell them from your own files.

## API

The package `order` of the example machine has these functions (`src/order/order.go`):

| Function | Result |
|---|---|
| `Initial() State` | the initial state |
| `Code(state State) (int32, error)` | the code of a state |
| `Key(state State) (string, error)` | the key of a state |
| `FromCode(value int64) (State, error)` | the state of a code; the argument is `int64`, so a value read from a database is passed as it is |
| `IsFinal(state State) (bool, error)` | whether a state is final |
| `EventsFrom(state State) ([]Event, error)` | the events that have an edge from a state, in declaration order |
| `Target(expected State, event Event) (State, error)` | the state that the event leads to; `E_INVALID_TRANSITION` when it has no edge |
| `Apply(expected State, event Event, actual State) (Step, error)` | the result of one attempt (see the root README, Transitions) |

`Step` has the fields `To State` and `Changed bool`. Each function returns its result and an `error`; the error is nil or a
`*fsm.Error`.

The persistence example `packages/fsm-go/examples/persist.go` contains the complete `Apply` use in a transaction, and it is the
pattern to copy (see Persistence). The pure call is the same for a value that is not in a database:

```go
step, err := order.Apply(order.StateDraft, order.EventNext, order.StateDraft)
// step == order.Step{To: order.StatePaid, Changed: true}, err == nil
```

This snippet was run in a temporary module with the generated files of this checkout; its output is:

```text
{2 true} <nil>
{2 false} <nil>
E_CONFLICT 1 3 1
```

The three lines are `Apply(draft, next, draft)`, `Apply(draft, next, paid)` (the state already reached: `Unchanged`) and
`Apply(draft, next, shipped)` (a conflict, printed from the `*fsm.Error` fields `Code`, `Expected`, `Actual`, `Event`).

## Errors

Every error is `error`; the concrete value is `*fsm.Error` (`src/fsm/fsm.go`):

| Field | Type | Meaning |
|---|---|---|
| `Code` | `string` | `E_CONFLICT`, `E_INVALID_TRANSITION`, `E_UNKNOWN_CODE` or `E_RESERVED_CODE` |
| `Message` | `string` | the message, which names the machine; `Error()` returns it |
| `Expected` | `int32` | the expected state code, or 0 when the error has none |
| `Actual` | `int32` | the stored state code, or 0 when the error has none |
| `Event` | `int32` | the event position (from 1), or 0 when the error has none |

Use `errors.As` to read the fields. `Code` values are constants of `fsm`: `fsm.CodeConflict` and so on. A zero field means
unset, because a state code is at least 1 and an event position starts at 1.

## Persistence

`examples/persist.go` is the pattern of `docs/spec/fsm.md`, B-4 on SQLite with polyspec orm. The stored state is a code in a
row. A transition runs in one transaction: the row is read under its lock, the event is applied to the state the caller
observed, and the row is written only when the result is `Changed`:

```go
// packages/fsm-go/examples/persist.go, Transition
func Transition(db *orm.DB, id int64, expected order.State, event order.Event) (order.Step, error) {
	var step order.Step
	err := db.Transaction(func() error {
		row, err := model.Item().Connect(db).ForUpdate().GetById(id)
		if err != nil {
			return err
		}
		state, err := order.FromCode(int64(row.GetStatus()))
		if err != nil {
			return err
		}
		step, err = order.Apply(expected, event, state)
		if err != nil {
			return err
		}
		if !step.Changed {
			return nil
		}
		code, err := order.Code(step.To)
		if err != nil {
			return err
		}
		_, err = row.SetStatus(code).Update()
		return err
	})
	if err != nil {
		return order.Step{}, err
	}
	return step, nil
}
```

An error of `Apply` returns from the callback, so the transaction rolls back and the stored state stays as it was. A retry
with the same `expected` returns `Unchanged` and writes nothing. The model `examples/model` is generated from
`schema/persist.dbs` by `go tool orm-gen`; `Open`, `Seed` and `StatusOf` in the same file create the tables and read a row.

## Tests

From the checkout (the modules must be downloaded once, online):

```sh
make -C packages/fsm-go install   # go mod download
make -C packages/fsm-go test      # GOPROXY=off, the conformance tests and the persistence example on SQLite
make test-go                      # the same from the root
```

The run passes 89 of 89 cases: `tests/conformance_test.go` runs one subtest per vector case of `tests/vectors_test.go`, named
`test_<feature>__<id>`. The root `make gen-check` checks that the generated files are the ones `fsm-gen` writes today. The go
toolchain is the one of `packages/fsm-go/go.mod` (`toolchain go1.27.2`).
