## Unreleased

- S-13-1: the rust package `packages/status-rust` is the kind `rust` of the canonical layout (`docs/plans/status-v1.md`, C-2). `make gen` writes its `src/` and `tests/vectors.rs` with status-gen; `build.rs` generates the orm models of the root `schema/persist.dbs` into `OUT_DIR`, so the package has no `examples/model/` (the declared difference of rust in `contracts/layout.json`). `tests/conformance.rs` holds the check functions, and the 89 vector cases run as `test_<feature>__<id>`; `examples/persist.rs` runs the B-4 transaction on SQLite with polyspec orm (`v0.0.7`, pinned by tag), and the persist cases assert the stored code after each run. `rust-toolchain.toml` declares Rust 1.98.0 at the root, and `config/toolchain.json` declares `cargoAudit` 0.22.2 for the dependency review of `Cargo.lock`. `make test-rust` and `make parity-rust` run the package, and `make packages-test` runs it with the other kinds.
- S-13: the rust backend (`packages/status-compiler/src/backends/rust.mjs`) generates the `src/` files of a rust package for every machine: `<machine>.rs` with the B-6 notation (`#[repr(i32)]` `State` and `Event`, the `Step` struct, the eight functions, `from_code` taking `i64`, `apply` returning `Result<Step, Error>`), the shared `status.rs` (`Code` and `Error`) and `lib.rs`. `status-gen vectors --kind rust --out <file>` writes `tests/vectors.rs`, one `#[test]` per case (`#[tokio::test]` for a persist case) that calls the check functions of `tests/conformance.rs`. The golden files under `packages/status-compiler/tests/golden/rust/` hold the order example; they were reviewed against B-6 before they were written, and tests compare them byte for byte.
- S-12-1: the php package `packages/status-php` is the kind `php` of the canonical layout (`docs/plans/status-v1.md`, C-2). `make gen` writes its `src/` and `tests/Vectors.php` with status-gen (`--php-namespace 'Polyspec\StatusTest'`) and `examples/model/` with orm-gen from the root `schema/persist.dbs`. `tests/ConformanceTest.php` runs each of the 89 vector cases as the PHPUnit data set `test_<feature>__<id>`, which `check-parity` reads as one case name per id; it uses the public API of the generated namespace only. The persist cases run the B-4 transaction on SQLite with polyspec orm v0.0.7 (the release zip, pinned by its sha1 in `composer.json`, with ordered-json v0.0.7) and assert the stored state after each run. `composer.json` pins PHPUnit 12.5.38 (the latest stable release at the review) and `config.platform.php` 8.4.0; `config/toolchain.json` declares PHP 8.5 and Composer 2.10.3, and `config/dependency-review.json` records the review. `make test-php` and `make parity-php` run the package.
- S-12: the php backend (`packages/status-compiler/src/backends/php.mjs`) generates the `src/` files of a php package for every machine: `<Pascal>/State.php` and `Event.php` (backed enums with the B-6 codes and indexes), `Step.php`, and `functions.php` with the functions of B-6 as namespace functions, and the shared `Status/Code.php` (enum of the error codes) and `Status/Error.php` (an `\Exception` whose `getCode()` is the code string). `status-gen gen --kind php --php-namespace <ns> --out <dir>` requires the namespace (`Polyspec\StatusTest` for the test bench), so a missing or malformed one is a usage error. `vectors --kind php --php-namespace <ns> --out <file>` writes `Tests/Vectors.php`, whose `cases()` keys every case by `test_<feature>__<id>`. A php file has `<?php` on its first line, so the header is read on the second line, and a file without it is still refused (`E_NOT_GENERATED`). The golden files under `packages/status-compiler/tests/golden/php/` hold the order example (89 cases); they were reviewed against B-6 before they were written, and `php -l` accepts every generated file.
- S-10-1: the go package `packages/status-go` is the kind `go` of the canonical layout (`docs/plans/status-v1.md`, C-2), module `github.com/polyspec/status-go`. `make gen` writes `src/` (`order/order.go`, `status/status.go`) and `tests/vectors_test.go` with status-gen, and `examples/model/` with orm-gen (`go tool orm-gen`, a `tool` directive of go.mod) from the root `schema/persist.dbs`; the models are generated inside the output directory, so gen-check runs them in a module copy. `tests/conformance_test.go` runs every vector case as the subtest `test_<feature>__<id>` against the generated functions, and `examples/persist.go` runs the B-4 transaction on SQLite with polyspec orm v0.0.7, which the persist cases assert after each run. `contracts/layout.json` declares the kind with its `generated` globs. Its language-forced differences are two: `gen --kind go` takes `--go-module` (the generated machines import the shared package by the module path), and the toolchain is the `toolchain` line of `packages/status-go/go.mod` (go1.27.2, which fixes the stdlib advisory GO-2026-6607 that go1.27.0 reports), read by `config/toolchain.json` `go`. `config/toolchain.json` also pins govulncheck 1.8.0, which the dependency review runs. `make test-go` (with `GOPROXY=off`), `make parity-go` and `make packages-test` run the package; the lock is `go.sum`, reviewed in `config/dependency-review.json`.
- S-10: the go backend (`packages/status-compiler/src/backends/go.mjs`) generates the `src/` files of a go package: `<machine>/<machine>.go` per machine with the B-6 notation (`type State int32` with the members `StateDraft`, `type Event int32` with `EventNext` (positions from 1), the struct `Step{To, Changed}`, and the functions `Initial`, `Code`, `Key`, `FromCode`, `IsFinal`, `EventsFrom`, `Target` and `Apply`, which return `(value, error)` with a `*status.Error` and check their arguments in the order of npm), and the shared `status/status.go` (the `Error` type and the `Code*` constants). `status-gen gen --kind go --go-module <module path> --out <dir>` writes that set; the module path is required because the machines import the shared package by it. `status-gen vectors --kind go --out <file>` writes the native `tests/vectors_test.go`: one literal per case, with the keys of the oracle, which the conformance test maps to the constants. The golden files under `packages/status-compiler/tests/golden/go/` hold the order example; they were reviewed against B-6 before they were written, and tests compare them byte for byte.
- S-16: the GUI skeleton (`packages/status-gui`) is a hyper v0.0.11 application. `/` lists the machines of the project with the crudui list of `crud/machines.yml`, and `/machines/{machine}` shows the states, the events with their edges and the canonical Mermaid text in `<pre class="mermaid">`, which the client renders with mermaid 12.1.0 on the first load and after every htmx swap. `node src/main.mjs --project <dir>` selects the store that `status.config.json` names (json, mermaid or db) and calls only that store and core `run`; every finding of the project is shown as an error, and an unknown machine answers 404. `make gui-test` builds the assets and runs 133 tests, which include the parse of the order example with the pinned mermaid package and the parse of every reserved Mermaid state key of B-5 at five positions. The pins are hyper v0.0.11, crudui v0.0.5, template v0.0.5, and exact versions of mermaid, htmx.org and yaml, reviewed in `config/dependency-review.json`. The criterion of the Mermaid parse test is recorded in `docs/spec/status.md`, B-5.
- S-09-1: the npm package `packages/status-npm` is the kind `npm` of the canonical layout (`docs/plans/status-v1.md`, C-2). `make gen` writes its `src/` and `tests/vectors.mjs` with status-gen and `examples/model/` with orm-gen from the root `schema/persist.dbs` (created here and shared by every kind). `tests/conformance.test.mjs` runs every vector case as `test_<feature>__<id>` against the generated functions, and `examples/persist.mjs` runs the B-4 transaction on SQLite with polyspec orm, which the persist cases assert after each run. `contracts/layout.json` declares the kind with its `generated` globs: `check-layout` requires them, and `gen-check` compares exactly the files they match. `make test-npm`, `make parity-npm` and `make packages-test` run the package, and the lock is in `config/dependency-policy.json` with its review record.
- S-09: the npm backend (`packages/status-compiler/src/backends/npm.mjs`) generates the `src/` files of an npm package for every machine: `<machine>.js` and `<machine>.d.ts` with the B-6 notation (frozen `State` and `Event`, the eight functions, `apply` returning `{to, changed}` or throwing `status.Error`), the shared `status.js` and `status.d.ts` (`Error` and the `Code` constants), and `index.js` and `index.d.ts`. `status-gen gen --kind npm --out <dir>` writes the set through `writeAtomic`, removes the stale files that carry the generated header and refuses a file without it (`E_NOT_GENERATED`, nothing written). `status-gen vectors --kind npm --out <file>` writes the native module `tests/vectors.mjs`. The golden files under `packages/status-compiler/tests/golden/npm/` hold the order example; they were reviewed against B-6 before they were written, and tests compare them byte for byte.
- S-15: the DB store (`packages/status-db/src/db-store.mjs`) keeps the definitions and the lock in the six tables of `schema/status.dbs` through the orm client (v0.0.7). `dbStore(db)` reads and writes through the models that orm-gen generates into `src/models/models.ts`, and `save` replaces every row inside one transaction, so a failed write leaves the rows that were there. Every key column is `varchar(64)`, the bound of S-05-3, and the edge table has the two indexes of its foreign keys to `state`. The store passes the store contract (`tests/store-contract.mjs`), round-trips json → db → json byte-identically with a 64-character key, refuses a copy into a non-empty database with `E_STORE_NOT_EMPTY`, and rolls back a failed save. `status-db` (`src/cli/status-db.mjs`) gives `check`, `lock` and `copy --to|--from json|mermaid --root`; its DSN is the value of the environment variable that `status.config.json` names. `make db-test` runs its tests, which include the check that orm-gen reproduces the committed models.
- S-06-1: the store contract is async. `load()` and `save()` of the JSON and Mermaid stores return Promises, and `run` and `copy` (`src/core/run.mjs`) are async, so the DB store can use the async orm client. `status-gen` awaits the commands, prints an unexpected rejection and exits 1. validate, normalize, lock and vectors stay synchronous. The store contract tests (`tests/store-contract.mjs`) await a Promise from every store, and every test that calls a store or a command awaits it.
- S-08: the Mermaid store (`src/store-mermaid/`) reads and writes `machines/*.status.mmd` in the canonical form of `docs/spec/status.md`, B-1: `parse.mjs` refuses every line outside that form with `E_MERMAID_UNSUPPORTED` and its line number, and `write.mjs` writes the form. `save` deletes the undefined `*.status.mmd` files and passes the store contract (`tests/store-contract.mjs`). The lock read and write moved to `src/store-lock/lock-file.mjs`, which both file stores share. `status-gen` accepts `{"store":"mermaid"}`, and `copy --to json|mermaid` migrates in both directions into an empty target; every valid fixture round-trips json → mermaid → json byte-identically.
- S-05-3: core `validate` bounds the length of machine, state and event keys to 64 characters: a key longer than 64 fails `E_KEY_FORMAT` at its path, with a message that names the length and the maximum. The DB store keeps keys in `varchar(64)`, so the bound lets all three stores accept the same keys (`docs/spec/status.md`, B-5).
- S-07: the root files of the conformance hold `status.config.json` (`{"store":"json"}`), `machines/order.status.json` (the order example of B-1, written by the JSON store), its `status.lock.json` and `contracts/features.json`. The core `vectors` (`src/core/vectors.mjs`) computes every case of C-4 from the IR and the lock; `status-gen vectors --out <dir>` writes `<machine>.json`, so `conformance/vectors/order.json` holds 89 cases. `scripts/gen-check.mjs` (`make gen-check`) regenerates the vector files into `var/gen-check/` and requires the tracked files of `conformance/vectors` to equal them, with `make gen-check-test` as its test.
- S-06: core `normalize` returns the IR of a valid definition (`src/core/normalize.mjs`); `lockMismatch`, `nextLock`, `nextCode` and `canonicalLock` implement the code lock of B-3 (`src/core/lock.mjs`), and `nextLock` refuses a key whose code the lock holds and the definition changes with `E_CODE_CHANGED`; `run` (`check`, `lock`, `save`) and `copy` run the commands of B-2 over a store (`src/core/run.mjs`). The JSON store (`src/store-json/store.mjs`) reads and writes `machines/*.status.json` and `status.lock.json` in canonical form and passes the store contract (`tests/store-contract.mjs`). `status-gen` (`src/cli/status-gen.mjs`) gives `check`, `lock` and `copy`; the mermaid store stays `E_STORE_NOT_CONFIGURED` until S-08.
- S-05-2: core `validate` reports the name and code errors of B-5, `E_KEY_FORMAT`, `E_DUPLICATE_KEY`, `E_KEY_RESERVED` (the fixed lists are in `packages/status-compiler/src/core/reserved.mjs`), `E_DUPLICATE_CODE` and `E_CODE_RANGE`. A machine key is compared after its underscores are removed, and a machine with a structural error is not compared with the other machines.
- S-05-1: core `validate` reports the graph errors of B-5, `E_UNKNOWN_STATE_REF`, `E_SELF_LOOP`, `E_NONDETERMINISTIC`, `E_DUPLICATE_EDGE`, `E_INITIAL_COUNT`, `E_FINAL_OUTGOING`, `E_UNREACHABLE` and `E_DEAD_END`, each with its own failing case. Reachability starts from the single initial state, and a machine with a structural error reports only its `E_SCHEMA` findings.
- S-05: core `validate` (`packages/status-compiler/src/core/validate.mjs`) reports every structural error of a definition as `E_SCHEMA` with its JSON path and skips the later rules of that machine. `schema/status.schema.json` is the editor schema, written with the keywords of kit `schema-validate.mjs`; the correspondence test checks that it and the core agree on every fixture. `make compiler-test` runs the tests through `run-tests.mjs` and records `.results/compiler-test.json`.
- The JSON store writes an edge as the object `{from, to}` instead of a pair, so the editor schema checks it exactly and a GUI form edits it as a row (`docs/spec/status.md`, B-1).
- S-04: `scripts/check-parity.mjs` (`make parity-check`, `make parity-<kind>` with `--kind`) fails unless every kind ran every vector case of `conformance/vectors` once and passed, from a current record that covers its package, every feature of `contracts/features.json` has a vector case, every test id names one case or is the parent of one, every tool test of `TOOL_TESTS` left a current passing record, and no record ran over 10 minutes. There is no exemption.
- S-03: `scripts/check-layout.mjs` (`make layout-check`) checks the language packages against `contracts/layout.json`: the package directories are exactly the tools and the kinds, every file of a kind matches its canonical layout, every canonical and required file exists, and the php and php-ext tests are the same bytes. `make layout-test` runs its tests through `run-tests.mjs` and records `.results/layout-test.json`.
- S-02: `docs/spec/status.md` fixes the definition: the model of three parts (machine, states with codes, events of edges), the three stores under one rule set, the lock of codes, the idempotent transition `apply(expected, event, actual)`, the validation codes and the naming rule of the six targets. The plan points to it, so the definition has one source.
- S-01: the repository adopts kit v0.0.14 (`scripts/kit/`, `tests/kit/`, `.kit/kit.lock.json`) with `config/checklist.json`, `config/commits.json`, `config/documents.json`, `config/owner-checks.json`, `config/toolchain.json` (Node.js only), `config/dependency-policy.json` and its review record; the hooks run the owner validation (pre-commit), the commit rules (commit-msg) and the push gate (pre-push). `AGENTS.md` holds the development rules, `docs/plans/status-v1.md` the plan and `docs/plans/execution-checklist.md` its items. `make check` runs the full suite once per tree.
