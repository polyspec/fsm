# polyspec-status-python

[한국어](README.ko.md)

The python consumer of status (`docs/plans/status-v1.md`, C-2). The package is private and is a test bed: it is not published.
It shows how the generated python code of a status definition is used, and it checks that code against the conformance vectors.

- `src/polyspec_status/`: generated by `status-gen gen --kind python` (do not edit). `order.py` holds the machine: `State` and
  `Event` as `IntEnum` classes with upper-case members, the frozen dataclass `Step` and the eight functions, which raise
  `status.Error`. `status.py` holds the `Code` `StrEnum` and the `Error` exception; `__init__.py` exports the modules.
- `tests/vectors.py`: the vector cases of every machine, generated by `status-gen vectors --kind python`.
- `tests/test_conformance.py`: one unittest method per vector case, named `test_<feature>__<id>`, which asserts the result of the
  generated function or its error code.
- `examples/persist.py`: the persistence pattern of `docs/spec/status.md` (B-4) on SQLite with polyspec orm. The persist cases
  run it.
- `examples/model/models.py`: the orm model generated from the root `schema/persist.dbs`.

## Python 3.14 environment

The checkout declares Python 3.14 in `config/toolchain.json` (`"python": "3.14"`). The package does not use the system
`python3`: on macOS `/usr/bin/python3` is 3.9, and the orm client requires Python 3.11 or later.

- `make install-python` (online, at the root) installs Python 3.14 into uv's own store (`uv python install --no-bin`, so uv
  writes nothing into a user bin directory such as `~/.local/bin`) and links `var/tools/bin/python3` to it. In the checkout,
  that link is the only change; no system path changes.
- `make install` (online) creates `.venv` with the interpreter named by `PYTHON` (default the absolute path of
  `var/tools/bin/python3` of the root, not a PATH lookup), refuses any other minor release, and installs this package in editable mode with its
  dependencies. The orm client is pinned in
  `pyproject.toml` to its git tag `v0.0.7`; orm pins its own dependencies exactly, so the install resolves the same packages from
  the same tag. The build backend is pinned too (`setuptools==84.0.0`). `.venv` is gitignored.
- `make test` (offline) puts `.venv/bin` first on `PATH` and runs the kit runner, which starts `python3`. That `python3` is the
  Python 3.14 of the venv, so the tests run on the declared release. The target creates nothing and needs no network. It
  refuses to run when `.venv` is missing.

## Reproduce from a clean checkout

```sh
make install-python                      # online: Python 3.14 with uv, linked into var/tools/bin
make -C packages/status-python install   # online: the venv and the pinned dependencies
make test-python                         # offline: the 89 vector cases and the persist cases
```

The generated files are committed, so `test` needs no generator. `make -C packages/status-python gen` regenerates them (it needs
`install`), and the root `make gen-check` checks that they are current. `make parity-python` checks the result record of every
case.

No lock file is committed for this kind: python has none in C-2, and the exact pins above fix the dependency tree.

## Root gates and the interpreter on PATH

The root Makefile puts `var/tools/bin` first on `PATH`, so the root `make toolchain-check` runs the `python3` that `make install-python`
linked, and compares its release with the declared 3.14. No system `python3` is changed, and no symbolic link outside the checkout
is needed. The package targets use the same `var/tools/bin` and then the venv.
