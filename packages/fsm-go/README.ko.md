# github.com/polyspec/fsm-go

[English](README.md)

fsm의 go 소비자(`docs/plans/fsm-v1.md`, C-2)다. 모듈은 비공개이며 test bed이고 공개하지 않는다. fsm 정의로부터 생성한 go 코드를
어떻게 쓰는지 보여주고, 그 코드를 conformance vector로 검사한다. `src/`의 생성 코드는 표준 라이브러리만 import하며, orm 패키지는
영속화 예제에만 필요하다.

## 프로젝트에 생성

`module example.com/app`처럼 `go.mod`가 있는 프로젝트의 module 안에서 생성기를 실행한다. `--out`은 그 module의 `src` 디렉터리다.
각 기계는 공유 `Error` 타입을 위해 `<module>/src/fsm`을 import하기 때문이다.

```sh
cd /path/to/app
fsm-gen gen --project /path/to/order-machines --kind go --go-module example.com/app --out ./src
```

```text
[fsm-gen] gen: ok
```

생성된 파일은 손으로 고치지 않는다. 정의를 바꿀 때마다 명령을 다시 실행한다. vector는 `fsm-gen vectors --kind go`로 자신의 test
파일에 쓴다. test bed는 `tests/vectors_test.go`에 쓴다.

## 생성 파일

| 파일 | 내용 |
|---|---|
| `src/fsm/fsm.go` | package `fsm`: `Error` 타입과 오류 code 상수 `CodeConflict`, `CodeInvalidTransition`, `CodeUnknownCode`, `CodeReservedCode`(값은 `E_CONFLICT` 등) |
| `src/order/order.go` | 기계마다 하나인 package `order`: 타입 `State`(`int32`, code), `Event`(`int32`, 1부터의 위치)와 `Step`, 상수 `StateDraft`…와 `EventNext`…, 기계의 함수 |

각 파일은 `// Code generated by fsm-gen from <machine>; DO NOT EDIT.`로 시작하므로 `fsm-gen gen`이 자신의 파일과 구별한다.

## API

예제 기계의 package `order`는 다음 함수를 가진다(`src/order/order.go`).

| 함수 | 결과 |
|---|---|
| `Initial() State` | 초기 상태 |
| `Code(state State) (int32, error)` | 상태의 code |
| `Key(state State) (string, error)` | 상태의 key |
| `FromCode(value int64) (State, error)` | code의 상태. 인자는 `int64`이므로 database에서 읽은 값을 그대로 넘긴다 |
| `IsFinal(state State) (bool, error)` | 상태가 최종 상태인지 |
| `EventsFrom(state State) ([]Event, error)` | 상태에서 edge가 있는 event, 선언 순서 |
| `Target(expected State, event Event) (State, error)` | event가 이르는 상태. edge가 없으면 `E_INVALID_TRANSITION` |
| `Apply(expected State, event Event, actual State) (Step, error)` | 한 번 시도의 결과(루트 README의 전이 절 참고) |

`Step`은 `To State`와 `Changed bool` 필드를 가진다. 각 함수는 결과와 `error`를 돌려준다. `error`는 nil이거나 `*fsm.Error`다.

영속화 예제 `packages/fsm-go/examples/persist.go`는 transaction 안에서 `Apply`를 완전하게 쓰는 예이며, 따라 할 패턴이다(영속화 절).
database를 거치지 않는 순수 호출은 다음과 같다:

```go
step, err := order.Apply(order.StateDraft, order.EventNext, order.StateDraft)
// step == order.Step{To: order.StatePaid, Changed: true}, err == nil
```

이 snippet은 이 checkout의 생성 파일을 쓴 임시 module에서 실행했다. 출력은 다음과 같다:

```text
{2 true} <nil>
{2 false} <nil>
E_CONFLICT 1 3 1
```

세 줄은 각각 `Apply(draft, next, draft)`, `Apply(draft, next, paid)`(이미 도달한 상태: `Unchanged`), `Apply(draft, next, shipped)`(충돌.
`*fsm.Error`의 `Code`, `Expected`, `Actual`, `Event` 필드를 출력했다)이다.

## 오류

모든 오류는 `error`이며, 실제 값은 `*fsm.Error`다(`src/fsm/fsm.go`).

| 필드 | 타입 | 뜻 |
|---|---|---|
| `Code` | `string` | `E_CONFLICT`, `E_INVALID_TRANSITION`, `E_UNKNOWN_CODE` 또는 `E_RESERVED_CODE` |
| `Message` | `string` | 기계 이름을 담은 메시지. `Error()`가 돌려준다 |
| `Expected` | `int32` | 기대한 상태 code. 없으면 0 |
| `Actual` | `int32` | 저장된 상태 code. 없으면 0 |
| `Event` | `int32` | event 위치(1부터). 없으면 0 |

필드는 `errors.As`로 읽는다. `Code` 값은 `fsm`의 상수다: `fsm.CodeConflict` 등. 0인 필드는 설정되지 않은 값이다. 상태 code는 최소 1이고
event 위치는 1부터 시작하기 때문이다.

## 영속화

`packages/fsm-go/examples/persist.go`는 SQLite와 polyspec orm 위에서 `docs/spec/fsm.md`, B-4의 패턴이다. 저장된 상태는 row의 code다.
전이는 한 transaction 안에서 실행한다. row를 잠금 아래 읽고, event를 호출자가 관찰한 상태에 적용하며, 결과가 `Changed`일 때만
row를 쓴다:

```go
// packages/fsm-go/examples/persist.go, Transition
func Transition(db *orm.DB, id int64, expected order.State, event order.Event) (order.Step, error) {
	var step order.Step
	err := db.Transaction(func() error {
		row, err := model.Item().Connect(db).ForUpdate().GetById(id)
		if err != nil {
			return err
		}
		state, err := order.FromCode(int64(row.GetStatus()))
		if err != nil {
			return err
		}
		step, err = order.Apply(expected, event, state)
		if err != nil {
			return err
		}
		if !step.Changed {
			return nil
		}
		code, err := order.Code(step.To)
		if err != nil {
			return err
		}
		_, err = row.SetStatus(code).Update()
		return err
	})
	if err != nil {
		return order.Step{}, err
	}
	return step, nil
}
```

`Apply`의 오류는 callback에서 돌아오므로 transaction이 되돌아가고 저장된 상태는 그대로 남는다. 같은 `expected`로 다시 시도하면
`Unchanged`가 되어 아무것도 쓰지 않는다. 모델 `examples/model`은 `go tool orm-gen`이 `schema/persist.dbs`로부터 생성한다. 같은 파일의
`Open`, `Seed`, `StatusOf`는 table을 만들고 row를 읽는다.

## 테스트

checkout에서 실행한다(module은 한 번 온라인으로 받아야 한다):

```sh
make -C packages/fsm-go install   # go mod download
make -C packages/fsm-go test      # GOPROXY=off, the conformance tests and the persistence example on SQLite
make test-go                      # the same from the root
```

실행 결과는 89개 case 중 89개 통과다. `tests/conformance_test.go`는 `tests/vectors_test.go`의 vector case마다 하나의 subtest를
`test_<feature>__<id>` 이름으로 실행한다. 루트의 `make gen-check`는 생성 파일이 `fsm-gen`이 지금 쓰는 것과 같은지 검사한다. go
toolchain은 `packages/fsm-go/go.mod`의 것(`toolchain go1.27.2`)이다.
